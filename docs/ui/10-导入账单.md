# 10 · 导入账单

从设置 →「记账」→「账单导入」、分享文件（`ROUTE_IMPORT_FILE_PREFIX`）进入。四阶段同页：选择文件 → 解析中 → 预览 → 完成。

源码：`app/src/main/java/com/controleco/app/ui/imports/ImportScreen.kt`（约 709 行）

---

## 1. 路由与入口

- 路由：`import`。
- 进入：
  - 设置 →「记账」→「账单导入」→ `settings/import` → 选择账单文件 → `import`
  - 分享文件：`vm.parseBillFile(uri)` 后直接 `navigate("import")`
- 离开：
  - 返回
  - 完成后「返回」
  - 完成后「继续导入」→ 清空状态回到阶段 0（不离开页面）
- 页面 `onDispose` 会 `vm.clearImportState()`，离开即丢弃未提交的解析结果。

## 5. 状态与数据流

### VM

- `parsedBill: ParsedBill?`
- `importError: String?`
- `importDone: ImportCommitResult?`
- `importDuplicateCount: Int?`（解析完成时先与账本比对，预览直接用这个条数）
- `importAccountPlan: ImportAccountPlan?`（只按**会写入**的行做账户匹配）
- `accounts`

### 去重口径（`data/imports/BillDeduper.kt`）

导入前按以下顺序与账本已有记录逐条比对，命中任一条即视为同一笔并跳过（每条已有记录只能抵消一条导入记录）：

1. **外部单号相同**：同一账单文件/同一笔交易重复导出；
2. **方向 + 金额相同，时间相差 ≤ 10 分钟**：覆盖通知/页面自动捕获（通常支付后几秒落库）；
3. **方向 + 金额相同，同一天且商户/商品名可对应**：覆盖手动记账（用户填写时间与支付时间可能不同）。“可对应”指片段完全一致或一方包含另一方（如「美团」与「美团平台商户」）；含 `*` 的脱敏账号不参与匹配。

方向或金额不同一律保留（避免把金额相近的两笔不同账单误删）。
比对范围是账单最早~最晚时间前后各放宽一天，只查本地账本，不依赖来源/账户。
提交前会再跑一次比对（解析到确认之间账本可能新增记录），实际以提交时结果为准。

### 本地

- `manual: Map<String, Long>`：未匹配支付方式的人工确认（支付方式文本 → 账户 id），`remember(bill)` 随文件重置。
- `resolved`：`accounts` 非空，且 `plan.isResolved(manual)`（所有组要么自动匹配、要么已人工确认）。
- `parsing`：文件已选、结果未到的中间态。
- `LaunchedEffect(bill, error)`：任一到达即 `parsing = false`。

### 账户自动匹配（`data/imports/ImportAccountPlanner.kt`）

账单每行的「收/付款方式」（支付宝）或「支付方式」（微信）先按文本分组，每组用
`PaymentInstrumentParser.parse(payMethod, "微信"/"支付宝")` 结构化成支付工具，再交给
`PaymentAccountResolver.resolve(...)` 在用户账户里找（5 级：精确名 → 卡尾号 → 银行+尾号 → 银行/产品名 → 渠道）。

- **银行卡不做渠道兜底**：账户里没有这张卡时保持未匹配，交给用户确认；否则银行卡消费会被误记到「微信零钱 / 支付宝」。
  实现上必须同时清空 `instrument.channel`——`resolve` 在 `channelLabel` 为空时会回落到 `instrument.channel`。
- **账单没写支付方式**的行单独成组，强制定为未匹配（无法判断走的是零钱还是银行卡）。
- 分组即“确认粒度”：同一段文本只需确认一次；`ImportAccountPlan.assignments(manual)` = 自动匹配 + 人工确认。
- 未匹配的组数 > 1 时额外提供「批量设为同一个账户」。
- 预览阶段「未匹配」的组不清空 `manual`：换文件才重置。

### 文件选择

`rememberLauncherForActivityResult(OpenDocument())`，`picker.launch(arrayOf("*/*"))`。
选择后：`parsing = true` → `vm.parseBillFile(uri.toString())`。

> 分享文件进入时，`AppNav` 已经调用过 `parseBillFile`，本页只需展示结果。

### 阶段优先级

1. `done != null` → 完成
2. `bill != null` → 预览
3. `parsing && error == null` → 解析中
4. 否则 → 选择文件（含错误）

### 预览数据

- `bill.source.displayName`：识别来源（微信/支付宝）。
- 条数：总 / 支出 / 收入；跳过“不计收支”“未完成”的条数。
- 退款：`refundCount`；导入**不做任何配对**——只知道哪些支出被退款了，不需要“配对/匹配”这个操作。
  微信「已全额退款」的原支出、支付宝「交易关闭」的原支出直接标 `REFUNDED_EXPENSE`（显示「已退」，不再计入支出）；
  微信部分退款（「已退款(¥X)」）的原支出**不标**（照常全额计入支出）；退款行记为收入 + `REFUND_INCOME`、`refundPending = false`。
- 预览只取前 **8** 条。
- 重复提示：`importDuplicateCount > 0` 时增加一行 `已与账本比对：M 条账本中已有，将自动跳过；本次实际导入 K 条。`；`K = bill.rows.size - M`。
- 账户区只在 `K > 0` 时出现：已匹配的按「支付方式 · N 条 → 账户名（jade）」逐行列出；未匹配的放进 `amberSoft` 卡片，
  每组一排 `EcoChip` 选账户，组数 > 1 时再加一条「批量设为同一个账户」。标题在全部确认后变为「未匹配账户已确认」。
- 账户为空时提示“暂无账户，请先在账户管理中添加”，禁用确认。
- 主按钮文案按状态分派：`文件里没有可入账的记录`（`bill.rows` 为空）/ `账本中已有这些记录`（K == 0）/
  `请先添加账户`（`accounts` 为空）/ `请先确认未匹配账户`（`!resolved`）/ `确认导入 K 条`。
  可点条件：`fallbackAccountId != null && K > 0 && resolved`。
- 空态拆成两种，避免把「全部重复」误读成「没有可导入的记录」：
  - `bill.rows.isEmpty()` → 标题「文件里没有可入账的记录」，正文带 `dataRowCount` / 跳过明细；
  - `K == 0` → 标题「账本中已有这些记录」。
- 确认导入：`onCommit(assignments, fallbackAccountId)` → `vm.commitImport(bill, accountByPayMethod, fallbackAccountId)`；
  逐行 `accountByPayMethod[row.payMethod.trim()] ?: fallback`。

### 完成

`ImportCommitResult`：`inserted`、`duplicated`、`accountCount`（实际写入的记录涉及多少个账户）；
显示「成功导入 N 条，跳过重复 M 条。」与「已按账单里的「收/付款方式」记入 X 个账户。」。
「继续导入」→ `reset()`（清 VM 状态 + `parsing=false`）。
「返回」→ `onBack()`。

## 7. 文案

- 顶栏：`IMPORT` / `导入账单`。
- 阶段条：`01 选择文件`、`02 预览`、`03 导入`、`04 完成`（注意：解析中显示的是 `02` 预览前的进度）。
- 选择区：`从本机选择账单文件`、`微信 xlsx / 支付宝 CSV`、`选择账单文件`。
- 页尾：`文件只在本机解析；导入会先与账本已有记录比对，重复的自动跳过。`
- 教程：`导出方法 / HOW TO`；微信 `我 → 服务 → 钱包 → 账单 → 右上角常见问题 → 下载账单 → 用于个人对账（xlsx 发送到邮箱）。`；支付宝 `我的 → 账单 → 右上角「…」 → 开具交易流水证明 → 用于个人对账（CSV 发送到邮箱）。`

- 预览：`识别为：{来源} 账单`、`共 N 条（支出 X，收入 Y）；已跳过不计收支 A 条、未完成 B 条。`、`其中退款相关 N 条（已入库：退款收入记入收入，被退款的原支出标记为「已退款」、不再计入支出）`、`已与账本比对：M 条账本中已有，将自动跳过；本次实际导入 K 条。`、`记入账户`、`已按账单里的「收/付款方式」自动选择账户；未匹配的请手动确认。`、`待确认账户` / `未匹配账户已确认`、`{N} 种 · {M} 条`、`{支付方式} · {N} 条`、`批量设为同一个账户`、`账单未写支付方式`、`暂无账户，请先在账户管理中添加`、`文件里没有可入账的记录` / `已读取 N 行明细，其中 A 条是「不计收支」、B 条状态未完成。请确认导出的是「用于个人对账」的明细，或换一个文件试试。`、`账本中已有这些记录` / `这 N 条记录都能在账本里找到对应条目，本次没有新增，无需重复导入。`、`确认导入 K 条` / `请先添加账户` / `请先确认未匹配账户`、`换一个文件`。
- 预览页脚：`预览只显示前 8 条；导入会与账本比对（同方向、同金额，且单号相同 / 时间相近 / 同日同商户），只写入缺失记录。账户按账单里的支付方式自动匹配，未匹配的确认后才能导入。`
- 完成：`导入完成`、`成功导入 N 条，跳过重复 M 条。`（M 含账本已有 + 同单号冲突）、`已按账单里的「收/付款方式」记入 X 个账户。`、`继续导入`、`返回`。
- 错误：`导入失败`、`重试`。

## 9. 坑与验收

**坑**

1. **页面离开即清空导入状态**（`onDispose`），这是有意避免残留；不要为了“回来还能看到”去掉。
2. 阶段优先级不能乱：`done` > `bill` > `parsing` > idle；否则完成页会被预览覆盖。
3. 预览只显示前 8 条，但「确认导入 N 条」的 N 是 `bill.rows.size` 全量；不要改成 8。
4. 无账户时确认按钮必须禁用；账户匹配只在解析时算一次（`plan` 只含会写入的行）。
5. **银行卡不要做渠道兜底**：`PaymentAccountResolver.resolve` 在 `channelLabel` 为空时会回落到 `instrument.channel`，
   所以 planner 除了传空 `channelLabel`，还要 `instrument.copy(channel = "")`；否则账户里没有的银行卡会被记到「支付宝 / 微信零钱」。
6. 退款记录永远入库、永远显示（不再有显示开关）：退款收入永远计入收入，被标「已退款」的原支出不再计入支出；**退款收入固定归「退款」分类**，预览行也按这个口径显示，不要回退成按商户名猜的分类。
7. 分享文件进入时不要重复调用 `parseBillFile`（`AppNav` 已调用）；否则会解析两次。
8. 文件选择用 `OpenDocument` + `*/*`，不是图片选择器；不要换成 `PickVisualMedia`。
9. `ImportStageBar` 只有 4 步，解析中仍显示“02 预览”之前的进度；这是现有设计，不要新增第 5 步。
10. 解析失败时 `parsing=false` 且 `error!=null`，会回到 idle + 错误卡；不要卡在转圈。
11. **导入只做标记、不做配对**：微信「已全额退款」、支付宝「交易关闭」的原支出标 `REFUNDED_EXPENSE`；
    没有标记的普通支出不能当候选，**不要按金额/商户猜哪笔退款对应哪笔支出**。
12. 导入的退款行一律 `refundPending = false`，不进待确认；重复导入的记录由去重键拦掉。
13. **去重只比对“方向 + 金额”都相同的记录**：不要放宽成只看金额，否则同额的多笔真实消费会被误删。
14. 去重是一对一抵消：账本里 1 条、账单里 2 条同额记录 → 只跳过 1 条、仍导入 1 条；不要把 `used` 标记去掉。
15. 预览的重复条数来自解析时比对，提交时会**重新比对一次**；两处不要合并成同一份结果缓存，
    否则解析后账本新增记录会导致统计与实际入库不一致。
16. 支付宝「等待确认收货」是已付款的担保交易，必须计入支出；只有「等待付款/支付中」这类未完成状态才跳过。
    状态判定还兼容空状态 /「交易完成」/「已收钱」，避免整份账单被误判为“没有可导入的记录”。
17. 空态必须区分「文件里没有可入账的记录」（`bill.rows` 为空，带 `dataRowCount` 说明读到了多少行）
    与「账本中已有这些记录」（全部重复）；两者混用会让用户误以为解析失败。
18. `ImportAccountSection` 的 `EcoRowDivider` 只接受 `inset`，不要传 `color`。

**验收**

- [ ] 四个阶段按优先级正确切换。
- [ ] 解析失败有错误卡 + 重试。
- [ ] 预览条数/收支/跳过/退款统计与文件一致。
- [ ] 预览的「其中退款相关 N 条」文案与实际入库一致（退款收入记入收入，被退款的原支出标记为「已退款」、不再计入支出）。
- [ ] 被标「已退」的原支出不再计入支出；部分退款的原支出照常全额计入支出。
- [ ] 账户为空时不能导入；账户匹配区域按支付方式自动带出账户。
- [ ] 账户里没有的银行卡保持「待确认」，未确认时确认按钮为「请先确认未匹配账户」且不可点。
- [ ] 未匹配的支付方式逐条选账户后其余不变，全部确认后按钮变为「确认导入 K 条」。
- [ ] 存在多个未匹配支付方式时，「批量设为同一个账户」能一次确认全部。
- [ ] 导入完成后每个账户下的记录数与账单里对应支付方式的条数一致。
- [ ] 账本里已有的记录（同单号 / 10 分钟内同额同向 / 同日同商户同额同向）预览时计入重复，不会被写入。
- [ ] 账本里没有的记录全部写入；同额不同商户、不同方向不会被误判重复。
