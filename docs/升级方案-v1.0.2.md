## 三、模块 A：预算口径（P0，核心）

### A0 先定口径（关键决策，必须先确认）

本地已有一个更强的「整体排除」开关 `countInStats`（不计入收支/预算/存款全部统计），新版 `budgetExcluded` 只排除**预算**。两者叠加时必须明确优先级，建议如下：

| countInStats | budgetExcluded | aaShares | 账单列表 | 账户余额 | 统计「实际支出」 | 预算卡 / 分类预算 / 预算对比 |
|---|---|---|---|---|---|---|
| 1 | 0 | 0 | 账面金额 | 变 | m | m |
| 1 | 0 | n | 账面金额 | 变 | m ÷ n | m ÷ n |
| 1 | 1 | n | 账面金额 | 变 | m ÷ n | **0** |
| 1 | 1 | 0 | 账面金额 | 变 | m | **0** |
| 0 | 任意 | 任意 | 显示 | 变（只看 `excludeFromAssets`） | 0 | 0 |

补充规则：

1. 收入行强制 `budgetExcluded = false, aaShares = 0`。
2. 退款顺序：**先按 `refundLinkId` 扣净额，再做 AA 折算**（`max(0, m − 已关联退款) ÷ n`），新版是「先 AA、无退款关联」，直接照抄会和本地退款模型打架。
3. `aaShares` 合法区间 2..99，0 = 未开启；1 归一化为 0。
4. UI 建议：`countInStats` 关闭时**隐藏或禁用「预算」区块**（已整体排除，再勾不计入预算只会造成双重语义），保存时归一化为 `budgetExcluded=false, aaShares=0`。

### A3 DAO 查询改写

本地现有两条口径查询：[observeSpendingTotal](file:///workspace/app/src/main/java/com/controleco/app/data/db/Daos.kt#L137-L160)、[observeSpendingCategorySums](file:///workspace/app/src/main/java/com/controleco/app/data/db/Daos.kt#L162-L186)，都带 `refundLinkId` 净额与 `countInStats` 闸门。改写方式：

1. **实际支出**（统计页 02 / 圆环）在原 `CASE` 内叠加 AA，保留净额与 `countInStats`：

```sql
CASE
  WHEN t.countInStats = 0 OR t.refundMark = 'REFUNDED_EXPENSE' THEN 0
  ELSE CASE
    WHEN t.aaShares >= 2
      THEN (MAX(0, t.amountCents - COALESCE(r.totalRefundCents, 0)) + t.aaShares / 2) / t.aaShares
    ELSE MAX(0, t.amountCents - COALESCE(r.totalRefundCents, 0))
  END
END
```

2. **计入预算的金额**：同样结构，最前面再加一档 `WHEN t.budgetExcluded = 1 THEN 0`。
3. 新增两个方法（与新版同名，便于对照）：

```kotlin
fun observeBudgetSpendingTotal(startMillis: Long, endMillis: Long): Flow<Long>
fun observeBudgetCategorySums(startMillis: Long, endMillis: Long): Flow<List<CategorySumRow>>
```

分类查询保持 `GROUP BY c.id, c.name ORDER BY totalCents DESC`，保证「各分类之和 = 总额」。

> 注意：不要照搬新版的 `refundMark` 单边口径，本地是 `refundLinkId` 差额口径，退款不足/超额的处理在新版里根本不存在。

## 十、主要风险

1. **口径三重叠加**（`countInStats` × `budgetExcluded` × `aaShares` × 退款净额）最容易出现「三处数字对不上」；A0 表格必须先被确认，再动 SQL。
2. **漏改 Kotlin 侧折算**：`homeBudgetMonthSpent / homeBudgetDaySpent / 预算日历` 不经 DAO，只改 SQL 会导致回看月份口径错误。
3. **UI 语义重叠**：本地「不计入统计」已包含预算，新增「不计入预算」若不联动，用户会勾出互相矛盾的组合。
4. **微信放宽误并**：属于产品取舍，需在帮助页与通知规则文档明示。
5. **GPLv3**：法律影响需要你确认，默认不引入。
6. **帮助页内容**：直接复制会讲错本地口径，必须改写后才能发布。
