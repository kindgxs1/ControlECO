## #1 微信 ⇄ 银行仅金额 + 时间去重

**上游改动**：`CrossChannelDedup` 新增 `payBankLink()` + `LinkReason { WECHAT_AMOUNT_ONLY, EVIDENCE }`，`CaptureCenter` 的 `findCrossChannelPending` / `findBankPendingForPayment` 把 `payEntryLinksBank` / `payBankLinked` 改为返回 `LinkReason?` 的 `payEntryLinkReason` / `payBankLink`。微信恒走金额+时间，支付宝/云闪付仍要求银行名/卡尾号线索。

**work-new 现状**：
- `CrossChannelDedup.payBankLinked()` 仍对所有支付渠道要求线索，微信支付页面/通知读不到银行卡，所以「微信扣款 + 银行动账」大概率合不上 → 记成两笔。
- `CaptureCenter.payEntryLinksBank`（L2211）和 `findBankPendingForPayment`（L2277）都直接调 `payBankLinked`。

**迁移步骤**：
1. `CrossChannelDedup.kt`：照抄上游新增 `LinkReason` 枚举与 `payBankLink()`；保留 `payBankLinked`（支付宝/云闪付仍用）。
2. `CaptureCenter.kt`：
   - `payEntryLinksBank(candidate, ledger): Boolean` → `payEntryLinkReason(...): LinkReason?`，内部调 `payBankLink`。
   - `findCrossChannelPending` 内 `filter` → `mapNotNull { candidate to reason }`，命中时打 `AppLog.i("Dedup", "...(${reason.name})...")`。
   - `findBankPendingForPayment` 同样改造。
3. `CrossChannelDedupTest.kt`：补微信同额同窗必合、支付宝无证据不合、多候选不合用例。

**改动文件**：`CrossChannelDedup.kt`、`CaptureCenter.kt`、`CrossChannelDedupTest.kt`

**验收**：
- [ ] 微信付款 100 + 招行扣款 100 短信（≤130s）→ 合并为 1 条
- [ ] 支付宝付款无银行线索 → 不合并
- [ ] 两条同额微信付款 + 一条同额银行动账 → ambiguous，保持独立

## #2 银行推送只认包名 + 同银行跨通道去重

### 2a 银行推送候选准入

**上游改动**：抽出 `CaptureHeuristics.isBankPushCandidate()`，只认 `BankLedgerRules.bankNameOfPackage(packageName)` 短名单。

**work-new 现状**：`CaptureCenter` L1461 已内联实现同样逻辑（`bankNameOfPackage(packageName) != null`），注释也是「2026-10-27 用户规则」。

**迁移决策**：**不需要移植**。行为已一致，只是没抽成纯函数；可顺手重构但非必须。

### 2b 同银行跨通道去重（短信 ⇄ 推送 ⇄ 页面）

**上游改动**：新增 `BankEventDedup` + `BankEventClaims`（内存 1:1 配对，130s 窗口，按通道登记吸收）。

**work-new 现状**：有自有实现 `findSameBankPending` + `CrossChannelDedup.isSameBankTransaction` + `cardTailCompatible`：
- 窗口 **90 秒**（`SAME_BANK_WINDOW_MS`）
- 无内存通道登记，靠查 `pendingDao.getMergeable()` + `candidates.size > 1 → keep separate`
- 卡尾号：`cardTailCompatible`（incoming 空则 true，existing 从 `paymentInstrument`/`note` 取尾号，空或相等才 true）
- 单独 `pageFirst` 分支处理「同包名页面先到、推送后到」

**差异与风险**：work-new 没有「1:1 按通道吸收」的内存保护。当同一笔先后到了 3 条通道，第 3 条命中前两条（同额同银行）会被判 ambiguous → 不合并 → 变两条账。上游 `BankEventClaims` 能精确吸收。

**迁移决策**：**可选增强**。
- 方案 A（保守）：保留 work-new 现有实现不动。现实中 3 条通道同笔到齐且有两笔同额的概率低。
- 方案 B（增强）：把 `BankEventClaims` 挂到 `findSameBankPending` 的命中出口，在 `mergeBankInfoIntoPending` 后 `claim(pendingId, key, channel, sourceAt)`；`findSameBankPending` 的候选过滤里加 `channel in claim.channels → 跳过`。改动小，可解决漏合并。

**改动文件（方案 B）**：新增 `BankEventDedup.kt`、`CaptureCenter.kt`（接入 `bankClaims`）

**验收（方案 B）**：
- [ ] 同一笔短信 → 推送 → 页面 三条通道，最终只有 1 条账
- [ ] 两笔真实同额消费各产生短信+推送，互不合并
- [ ] 进程在 130s 窗口内重启后，标记丢失（已知边界）

## #3 悬浮卡按字段保护用户改过的内容

**上游改动**：
- 新增 `GuardedField { AMOUNT, COUNTERPARTY, NOTE, CATEGORY, ACCOUNT }` 和 `OverlayFieldGuards`（内存登记簿）
- `ConfirmCardState` 新增 `noteUserEdited`、`editedFields`；「商户 / 备注」拆成两个输入框
- `onConfirm` / `DismissSnapshot` 签名扩展为 `(amount, category, account, counterparty, note, editedFields)`
- `saveEnteredEdits` → `OverlayFieldGuards.mark(dedupKey, editedFields)`；`PendingActions.updateEntered` 不再 `markUserEdited`
- `mergePageInfo(..., guarded)` 逐字段跳过；`mergeBankInfoIntoPending` 按 `lockNote`/`lockCounterparty` 跳过
- 旧 `userEdited==true` 条目仍整条锁定（兼容）

**work-new 现状**：
- 仍是整条 `userEdited` 布尔，`updateEntered` 仍 `markUserEdited`（`PendingActions.kt` L130）
- `ConfirmCardContent` 只有一个「商户 / 备注」输入框，`onValueChange` 只调 `updateCounterparty`，`note` 不可单独编辑
- `ConfirmCardState` 多了 `excludeFromAssets` / `countInStats` 两个开关及 `assetUserEdited` / `statsUserEdited`（work-new 特有）
- `mergePageInfo` / `mergeBankInfoIntoPending` 仍 `if (existing.userEdited) return 原值` 整条锁定

**迁移步骤**：
1. 新增 `GuardedField`（放在 `CaptureMerge.kt`）和 `OverlayFieldGuards.kt`。
2. **`GuardedField` 扩到 7 个**：`AMOUNT, COUNTERPARTY, NOTE, CATEGORY, ACCOUNT, ASSET, STATS`（对应 work-new 的 资产/统计开关）。
3. `ConfirmCardContent.kt`：
   - 拆「商户 / 备注」为两个 `EcoField`，备注框 `onValueChange` 调新增的 `updateNote`
   - `ConfirmCardState` 加 `noteUserEdited`、`editedFields`（含 ASSET/STATS）
   - `onConfirm` 签名扩展为 6 参数
4. `ConfirmCardWindow.kt` / `OverlayDecision.kt`：`DismissSnapshot` 加 `note` + `editedFields`。
5. `CaptureCenter.kt`：
   - `retryCardIfNoCard` 前先做 #4 的 `wasShown` 闸门（同一次改动）
   - `saveEnteredEdits` 加 `editedFields` 参数 → `OverlayFieldGuards.mark`；`ignoreEntered`/`confirmFromOverlay`/`ignoreFromOverlay` 加 `OverlayFieldGuards.clear`
   - `mergeBankInfoIntoPending` 加 `guarded`，按 `lockNote`/`lockCounterparty`/`lockAccount` 跳过
   - `mergePageIntoExisting` → `mergePageInfo(..., guarded)`
6. `CaptureMerge.mergePageInfo`：加 `guarded: Set<GuardedField>` 参数，逐字段判断（`legacyLock = existing.userEdited` 兼容旧条目）。
7. `PendingActions.updateEntered`：去掉 `pendingDao.markUserEdited`，加 `note` 参数，`updateEnteredFields` 签名扩展。
8. `PendingActions.confirm`：加 `note` 参数（已在上游版本里，work-new 确认是否已有）。

**改动文件**：`CaptureMerge.kt`、`OverlayFieldGuards.kt`（新）、`ConfirmCardContent.kt`、`ConfirmCardWindow.kt`、`OverlayDecision.kt`、`CaptureCenter.kt`、`PendingActions.kt`

**验收**：
- [ ] 用户在卡片里只改了商户，后续页面富化不改商户，但可补备注/支付工具
- [ ] 用户改了备注，后续富化不覆盖备注
- [ ] 旧 `userEdited` 条目仍整条锁定
- [ ] 确认入账 / 忽略 / 撤销后 `OverlayFieldGuards` 被清理
- [ ] `excludeFromAssets` / `countInStats` 开关改动后，后续富化不覆盖

## #4 同一笔只弹一次悬浮卡

**上游改动**：新增 `OverlayPromptLog`（内存，按 `dedupKey`，上限 500）；`ConfirmCardWindow.showConfirm` 成功 `addView` 后 `markShown`；`retryCardIfNoCard` 里 `if (wasShown) return`，只静默富化。

**work-new 现状**：完全没有。`retryCardIfNoCard` 无闸门，同笔被后续通道捕获时会再次弹卡 → 用户可能误点「忽略」删掉唯一那笔已入账的账。

**迁移步骤**：
1. 新增 `OverlayPromptLog.kt`。
2. `ConfirmCardWindow.showConfirm` 成功路径加 `OverlayPromptLog.markShown(pending.dedupKey)`。
3. `CaptureCenter.retryCardIfNoCard` 开头加：
   ```kotlin
   if (OverlayPromptLog.wasShown(pending.dedupKey)) return
   ```
4. `ignoreEntered` / `confirmFromOverlay` / `ignoreFromOverlay` / 通知撤销入口加 `OverlayPromptLog.clear(dedupKey)`。
5. 保留 `refreshCardIfShowing`（正在展示的卡片仍刷新，不受此限）。

**改动文件**：`OverlayPromptLog.kt`（新）、`ConfirmCardWindow.kt`、`CaptureCenter.kt`

**验收**：
- [ ] 同笔首次弹卡后，页面富化不再弹第二张，只刷新正在显示的卡片
- [ ] 首次被支付保护层拦截（未成功展示）时，富化仍可补试一次
- [ ] 确认/忽略/撤销后登记簿清理，同 dedupKey 新交易可正常弹卡
- [ ] 进程重启后标记丢失（已知边界，用户可接受）

## #5 年视角柱状图按会计月分桶

**上游改动**：`ChartMath.yearBars` 加 `startDay: Int = 1` 参数；分桶从 `d.monthValue` 改为 `MonthPeriod.of(d, startDay).start` 的自然月归属；先按会计年区间过滤。

**work-new 现状**：`yearBars(rows, month, zone)` 仍是旧实现 `if (d.year == month.year) { i = d.monthValue - 1 }`；`StatsScreen` L167 调用 `yearBars(rowsReady, month)` 没传 `monthStartDay`（虽然 L119 已取到）。当 `monthStartDay ≠ 1` 时，次年 1 月初的账单被静默丢弃，柱子合计 < 封面实际支出。

**work-new 的 `MonthPeriod` 已有** `year(year, startDay)`、`of(date, startDay)`、`contains`、`.start`、`monthOf(date, startDay)`——API 完备。

**迁移步骤**：
1. `ChartMath.yearBars` 签名加 `startDay: Int = 1`，分桶逻辑替换为上游版本（可直接用 `MonthPeriod.monthOf(d, startDay)` 简化）。
2. `StatsScreen` L167 改为 `ChartMath.yearBars(rowsReady, month, monthStartDay)`。
3. 补上两个单测：首日=5 的跨年归属、首日=1 与旧行为等价。

**改动文件**：`ChartMath.kt`、`StatsScreen.kt`、`ChartMathTest.kt`

**验收**：
- [ ] `monthStartDay = 5` 的年份视图，次年 1 月 1–4 日的账单归入上一年 12 月桶
- [ ] 柱子合计 = 封面实际支出
- [ ] `monthStartDay = 1` 时与旧行为完全一致

## #6 收入「退款」分类锁定 + 启动自动补回

**上游改动**：新增 `CategoryRules.kt`（纯函数：`isLocked`、`editError`、`deleteError`、`duplicateNameError`），锁定「其他」和收入「退款」；`LedgerViewModel.init` 启动时若无「退款」则补建（`sortOrder = 3`）。

**work-new 现状**：
- 已有 `RefundCategory.NAME = "退款"` 和兜底链（退款 → 收入「其他」 → 第一个收入分类），导入不会因缺分类失败
- **没有**锁定「退款」改名/改类型/删除（只有一级「其他」被锁）
- **没有**启动自动补回
- 还有 `AACategory`、`ReimbursementCategory`（v1.0.12 特性），同样未锁定

**迁移步骤**：
1. 新增 `CategoryRules.kt`，但 `isLocked` / `editError` / `deleteError` **扩展**为覆盖三类收入保留分类：「退款」、`AACategory.NAME`、`ReimbursementCategory.NAME`。
2. `LedgerViewModel.saveCategory` / `deleteCategory`：把内联的「其他」校验替换为 `CategoryRules.editError` / `deleteError`；重名校验替换为 `CategoryRules.duplicateNameError`。
3. `LedgerViewModel.init`：启动时若无收入「退款」则补建（`sortOrder = 3`）。AA/报销分类按需在首次关联时创建，不建议启动时补。
4. `CategoriesScreen`：`isFallback` → `isLocked = CategoryRules.isLocked(category)`，名称行/类型分段/删除按钮统一按它禁用。
5. **保留 work-new 的兜底链**（比上游健壮），只叠加锁定 + 补回。

**改动文件**：`CategoryRules.kt`（新）、`LedgerViewModel.kt`、`CategoriesScreen.kt`、`CategoryRulesTest.kt`（新）

**验收**：
- [ ] 收入「退款」分类不可改名、不可改类型、不可删除
- [ ] AA/报销收入分类同样不可改名/改类型/删除
- [ ] 「其他」仍不可改名/改类型/删除
- [ ] 删除「退款」分类后重启，自动补回一个
- [ ] 导入账单时若「退款」存在则归到它，不存在则走兜底链不失败
